## Why earlier attempts failed (and the real root cause)

Two prior deploys (`xtrata-v3-2-2` nonce 229, `xtrata-v3-2-3` nonce 230 via the
wallet) aborted with `VM Error: use of unresolved function 'as-contract'`.

- **Misdiagnosis:** initially attributed to `(as-contract tx-sender)` sitting in
  a `define-constant`. That was cleaned up (inlined into the function bodies)
  but did **not** fix the deploy.
- **Real cause:** the wallet (Xverse / `@stacks/connect`) publishes contracts at
  the network's **latest Clarity version** and ignores the `clarityVersion`
  hint. On mainnet that is **Clarity 4**, where `as-contract` no longer resolves.
  `clarinet check` passed because the project pins these contracts to Clarity 3.
  Reproduced locally: same source under `clarity_version = 4` →
  `error: use of unresolved function 'as-contract'`.

## The fix

Deploy via the SDK with `ClarityVersion.Clarity3` pinned, bypassing the wallet's
version defaulting entirely. See `scripts/mainnet-v3.2.3-deploy.mjs`. All
post-deploy admin/migration/mint calls also go through the SDK
(`scripts/mainnet-v3.2.3-admin.mjs`) for a wallet-independent ceremony.

## Deployer derivation gotcha

The deployer `SP3J…743X` is the **4th wallet** in the shared mnemonic, derived
**account-hardened** at `m/44'/5757'/3'/0/0` (Xverse style). `@stacks/wallet-sdk`'s
default `m/44'/5757'/0'/0/{i}` does NOT reach it (that increments the address
index, not the hardened account index). Account index 0 of the same mnemonic is
`SP10W2EEM757922QTVDZZ5CSEW55JEFNN30J69TM7`. Probe tool:
`scripts/find-derivation.mjs` (prints addresses only, never keys).

## Sequencing rule

`set-next-id` must run **before** any mint or migration: its guards require
`next-id = 0` and `minted-count = 0`. Any migration/mint bumps `minted-count` and
would permanently block the one-shot offset with `ERR-ALREADY-SET`. Correct
order: deploy → pause old core → set-next-id → migrate → (royalty) → unpause →
mint announcement.

## Wallet client fix (bonus)

`src/lib/wallet/connect.ts` previously routed only Leather through the modern
`stx_deployContract` / `stx_callContract` / `stx_transferStx` request methods and
forced every other wallet (Xverse) down the legacy popup flow, which current
Xverse rejects with "Unexpected error creating transaction". Now any provider
exposing a `request()` bridge uses the modern method, with the legacy popup kept
only as a fallback. This repairs the handover UI for Xverse across all versions.
